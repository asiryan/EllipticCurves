Основные вычислительные утверждения архива воспроизвелись. Семейство действительно
содержит указанную кривую ICARM №302; опубликованные 31 точка дают безусловную
нижнюю границу 31. Быстрый отбор параметров работает, но не находит эти 31 точку
заново и не доказывает высокий ранг новых кандидатов.

## Что означает восстановленное семейство

[История комментариев ICARM](https://elliptic-rank.icarm.cloud/curve/302/commentary-history)
содержит формулу, добавленную 13 сентября 2026 года. Это внешний источник формулы,
а не результат её вывода из коэффициентов исследуемой кривой.

Семейство записано как

\[
y^2-(Lx+B)y=x(x+D)(x+E),\qquad
B=pq(L+p+q)-pE-qD.
\]

Здесь `L,p,q` — квадратичные, а `D,E` — многочлены четвёртой степени по `T`.
Точные коэффициенты перенесены в `tools/RankPackageAudit/Family302.cs`.
Подстановка `T=u/v` с однородными многочленами и заменой
`X=v^4 x`, `Y=v^6 y` даёт целочисленную модель
`[a1,a2,a3,a4,a6]=[-L,D+E,-B,D*E,0]`.

Из самой формы сразу следуют четыре точки:

\[
(0,0),\quad(-D,0),\quad(-E,0),\quad(-pq,-p(E-pq)).
\]

Первые три лежат на одной прямой, поэтому их сумма в группе равна нулю.
Четыре перечисленные точки нельзя считать четырьмя независимыми точками.
На проверенных специализациях `0/1`, `-58/237` и `164518/924945` проект
подтвердил нижнюю границу 3 по этому набору. Это не вычисление точного общего
ранга семейства и не утверждение, что других рациональных сечений нет.

При рекордном параметре проверено полное преобразование коэффициентов через
`ChangeModel`, затем все 31 точка перенесены на модель семейства через `MapBack`.
Совпадение одного `j`-инварианта не использовалось как доказательство изоморфизма.

Пакет не выводит семейство из произвольного уравнения и не раскрывает,
как первооткрыватели нашли исходное семейство и все рекордные точки.
Нельзя заключить, что именно CRT-алгоритм из этого архива использовался авторами рекорда.

## Как устроен быстрый поиск

Для каждого небольшого простого `p` предварительно подсчитываются точки всех
редукций семейства при `T` в проективной прямой над `F_p`. Сохраняется вклад

\[
s_p(T)=\log\frac{p+1-a_p(T)}p,\qquad
a_p(T)=p+1-\#E_T(\mathbf F_p).
\]

В реализации пропускаются простые 2 и 3 и сингулярные редукции отображаемой модели.
Такая модель может быть неминимальной: пропуск здесь означает сингулярность именно
используемого уравнения, а не доказательство плохой редукции минимальной кривой.

При фиксированном знаменателе `v` вклад в балл числителя `u` периодичен по модулю
`p`. Вместо повторного вычисления всей кривой строится короткий массив периода
`p`, который последовательно прибавляется к массиву баллов. Начальные баллы
масштабируются на `2^20` и суммируются целочисленно. Далее отбор идёт ступенями:

1. Все 4 866 351 примитивных параметра оцениваются по простым до 1021.
2. Сохраняются 2048 лучших; для них добавляются простые до 4093.
3. Сохраняются 32 лучших; для них добавляются простые до 16381.
4. Эти финалисты пересчитываются до 65521.

Подобное периодическое решето и последовательные фильтры описаны в
[работе Elkies–Klagsbrun, разделы 2–3](https://arxiv.org/html/2003.00077v1).
Баллы служат эвристикой выбора кривых для дальнейшего поиска точек.
Они не являются ни нижней границей ранга, ни вероятностью высокого ранга.

Параметр рекорда имеет знаменатель 924945 и вообще не входит в проверенный
прямоугольник с высотой 2000. В таблицы он добавляется отдельной строкой
`published_record_control`. Поэтому результат нельзя описывать как повторное
нахождение рекорда за пять секунд.

CRT-метод выбирает хорошие остатки параметра по небольшим простым и пересекает
двумерные решётки условий `u ≡ t*v (mod p)`; бесконечному параметру соответствует
`v ≡ 0 (mod p)`. После редукции базиса ищутся короткие примитивные векторы.
Ограниченное число сохраняемых ветвей делает это эвристическим поиском,
не гарантирующим охват всех хороших параметров. В воспроизведённом запуске
сам рекордный параметр среди 256 сгенерированных кандидатов отсутствует.

По простым `p>37`, не участвовавшим в генерации CRT, лучший итоговый кандидат
`109321/104861` набрал 19,278971673, а рекордная кривая — 22,223591044.
То есть оптимизация остатков на выбранных малых простых не обеспечила превосходства
на последующих простых. При этом часть последующих простых используется и для
промежуточного отбора до 4093; это проверка вне набора генерации CRT, а не полностью
нетронутый статистический тест после всех этапов выбора победителя.

## Как доказывается нижняя граница

Точки сначала точно проверяются подстановкой. Затем локальные квадратичные
характеры отображают классы точек по модулю удвоения в бинарные векторы.
Ранг матрицы над `F_2` с поправкой на размерность рационального 2-кручения даёт нижнюю
границу ранга. Проверяющий код пересчитывает простоту чисел, корни многочлена,
значения характеров и ранг, а не доверяет записанному числу 31.

Это вариант известного метода; математическая основа изложена в
[Cremona, On the computation of Mordell-Weil and 2-Selmer Groups of Elliptic Curves](https://johncremona.github.io/papers/filter.pdf).
Независимость уже данных точек часто проверяется очень быстро. Быстрота
проверки не означает, что сами точки столь же легко найти. Недостаточный ранг
матрицы тоже не доказывает зависимость точек: доступных характеров может не хватить.

Для `T=0` использовалась минимальная модель

\[
y^2+xy=x^3-39825758704928159405x+96877705862918645565273203025.
\]

Существующий `SearchRankLowerBound` получил только это уравнение с областью
целочисленного поиска `|x|≤10^10`, пределом времени 10 с и целью 12.
Он вернул 13 точек; доказанная нижняя граница 12 дополнительно проверена Python.
Архивный драйвер PARI, в отличие от этого запуска C#, использует три начальные
точки семейства. Новый запуск PARI вернул `[12,12]`, но в рамках этой проверки
безусловно подтверждается только нижняя граница: требуемая для верхней границы
отдельная сертификация не выполнялась.

Для `T=-58/237` подтверждены принадлежность элементарных точек, нижняя граница 3
и высокий поисковый балл. Архив сообщает о тайм-ауте PARI через 90 с; этот
дорогой запуск повторно не выполнялся. Из имеющихся данных не следует ранг 31,
32 или даже превосходство над специализацией `T=0`.

## Что это даёт проекту

Текущий `explorer/Models/ElkiesSearchFamily.cs` реализует другое семейство,
с 17 исходными сечениями. Его нельзя отождествлять с семейством ICARM №302.
Новый проверочный стенд использует библиотеку проекта, но пока не подключён
к интерфейсу Explorer.

Важная деталь производительности: для таблиц нужны вычисления непосредственно
над `F_p`. В текущем проекте вызов `EllipticCurveQ.CountPoints(p)` сначала строит
глобальную минимальную модель, что может запустить дорогую факторизацию больших
чисел. В стенде независимая проверка использует `EllipticCurveFp`, а быстрый
подсчёт — модульные коэффициенты и конечные разности. Для пропуска сингулярных
редукций отображаемой модели глобальная минимизация не требуется.

| Участок проекта | Практическое продолжение |
|---|---|
| `ElkiesSearchFamily` | Выделить общий интерфейс семейства; №302 добавить отдельной реализацией с собственной формулой и источниками точек |
| `CurveSearchEngine.Score` | Перенести периодическое накопление баллов из стенда; сейчас таблицы читаются для каждого параметра отдельно |
| `CurveSearchEngine.Inspect` | Выполнять дорогие проверки после нескольких ступеней отбора, сохраняя промежуточные кандидаты |
| Генерация параметров | Добавить CRT как отдельный вариант с явным списком использованных простых |
| Поиск точек | Развивать поиск на минимизированных и редуцированных накрытиях после спуска; в собственном коде проекта такого этапа пока нет |
| Результат | Хранить отдельно балл, точки из формул/публикаций, найденные поиском точки и доказанную нижнюю границу |

Для ранее выбранной задачи «на входе только уравнение произвольной кривой»
семейное решето не заменяет поиск рациональных точек. Оно выбирает кривые из
заранее заданного семейства. Ближайшая сложная часть универсального поиска —
построение и редукция вспомогательных накрытий, поиск на них и перенос точек
обратно с точной проверкой независимости. Это направление не даёт гарантии
быстрого положительного результата для любого входа.

## Файлы и воспроизведение

Команды выполняются из корня репозитория. Нужны .NET 8, Python 3 и локальный
PARI/GP для повторения соответствующего опыта. NuGet-зависимости проекта должны
быть доступны локально или восстановлены обычным способом.

Распакованный оригинал находится в
`artifacts/rank-package-audit/original/elliptic_rank_search`; результаты — в
`artifacts/rank-package-audit/reproduced`. Оригинальные файлы не редактировались.
Каталог `artifacts` игнорируется Git; исходники стенда в `tools/RankPackageAudit`
и этот отчёт находятся вне игнорируемого каталога.

```powershell
python artifacts/rank-package-audit/original/elliptic_rank_search/verify.py

python artifacts/rank-package-audit/original/elliptic_rank_search/crt_beam.py --output artifacts/rank-package-audit/reproduced/crt_candidates.tsv

python artifacts/rank-package-audit/original/elliptic_rank_search/gp_driver.py --gp artifacts/native-validation/gp.exe --u 0 --v 1 --effort 1 --timeout 90 --output-prefix artifacts/rank-package-audit/reproduced/gp_t0

dotnet run --project tools/RankPackageAudit/Audit.csproj -c Release -- --sieve

python tools/RankPackageAudit/verify_outputs.py
```

Без `--sieve` C# выполняет только математические проверки и поиск для `T=0`.
Полный запуск сохраняет `project_audit.json`; сокращённый — `project_core_audit.json`.
Сверка архивных и воспроизведённых результатов сохраняется в `output_audit.json`.
Найденные C# точки сохранены в `csharp_t0_equation_only.json` вместе с отдельным
проверяемым сертификатом. Стенд фиксирует параметры этого эксперимента и не
претендует на законченный пользовательский интерфейс общего поиска.
