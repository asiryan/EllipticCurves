# Воспроизведение 31 точки ICARM302

14 сентября 2026 года получены все **31 опубликованная точка**, в том же
порядке и с теми же рациональными координатами. C# и отдельный Python-код
подтвердили их независимость по модулю кручения и нижнюю границу **31**,
без дополнительных гипотез. Точный ранг и верхняя граница не вычислялись.

Это **воспроизведение с помощью известных ответов**: опубликованные точки
использовались в диагностике для выбора опорных точек, моделей, размеров
области поиска и коротких представителей. Это не эксперимент «только
уравнение на входе», не новый рекорд и не установление оригинального метода
авторов. Источник сравнения — [ICARM302](https://elliptic-rank.icarm.cloud/curve/302),
локальная копия — `tests/Fixtures/icarm-302.json`.

Итоговые точки: [points31.json](../results/record-reproduction-20260914/points31.json).
Проверки: [summary.json](../results/record-reproduction-20260914/summary.json).
Полная последовательность: [operations.json](../results/record-reproduction-20260914/operations.json).

## Что мешало предыдущему поиску

Наши исходные 17 точек и следующие 17 опубликованных точек порождают
**одну и ту же подгруппу**:

`2, 5, 7, 8, 10, 11, 12, 15, 16, 18, 20, 21, 23, 24, 25, 27, 28`.

Найдена целочисленная матрица перехода с определителем −1 и целочисленная
обратная матрица. Все равенства проверены точными операциями на кривой.
Численные канонические высоты использовались только для предположения
коэффициентов. Поэтому несовпадение исходных координат не означало потери
какого-либо из этих 17 направлений. Смена базиса сама по себе ранг не увеличила.

Основная проблема была в представлении задачи. На первоначальных 17
квартиках ближайшая из недостающих опубликованных точек требовала высоты
как минимум `4372619865531907`, тогда как поиск ограничивался `100000`.
Проверки прямых и обратных отображений подтвердили эту разницу точно.

## Выполненные доработки

1. Добавлена минимизация каждой квартики перед редукцией и точная композиция
   обратных преобразований. Исправлена обработка рациональных точек на
   бесконечности квартики: они могут давать конечные точки исходной кривой.
2. Опорные точки строятся как короткие целочисленные комбинации уже известных
   точек. Для выбора используются матрица канонических высот, LLL и ограниченный
   перебор векторов. Все выбранные комбинации независимо пересчитываются
   точной арифметикой Python. Само построение опор новых направлений не добавляет.
3. Разделены ограничения на числитель и знаменатель. Область поиска имеет вид
   `|n| ≤ N, 1 ≤ d ≤ D` для координаты `n/d`, вместо одинакового большого
   ограничения по обеим осям. Это существенно сократило перебор.
4. Для последних точек добавлено сокращение представителя по уже известной
   подгруппе. Диагностика выбирает `R = Q + Σ cᵢPᵢ`, где `Q` — опубликованная
   точка, а `Pᵢ` уже найдены. Поисковая программа должна действительно вернуть
   `R`; лишь после этого точные операции восстанавливают `Q = R − Σ cᵢPᵢ`.
   Так получены опубликованные №29 и №31.

Последний шаг показывает, почему полезно сохранять точки, не совпадающие
с опубликованным списком: подходящий представитель может быть значительно
доступнее для поиска. Программа запрещает восстановление, если представитель
или используемая известная точка отсутствует в уже полученном наборе.

## Проверка происхождения и независимости

`save_record_reproduction.py` заново вычислил 17 начальных точек из формул
семейства и проверил смену базиса. Затем для каждого успешного поиска он:

- восстановил опорную точку как целочисленную комбинацию ранее полученных;
- заново сгенерировал GP-скрипт только из разрешённых входных данных
  и сравнил его с реально исполненным скриптом;
- сравнил сохранённый результат с точным объединением предыдущих точек
  и строк `POINT` из stdout;
- проверил восстановление двух опубликованных точек из найденных представителей.

Все проверки прошли. Недостающие координаты не добавлялись в результаты
вместо поиска. Данные эталона при этом действительно влияли на выбор
стратегии; этот факт отмечен в итоговом JSON.

Сертификат C#: `point_count=31`, `LowerBound=31`, `ImageDimension=31`,
`NoTwoTorsionPrime=31`, список гипотез пуст. Отдельный Python-сертификатор
получил размерность 31, отсутствие рационального 2-кручения и независимость
всех 31 точек. Его код, сертификат и результат проверки сохранены вместе
с точками. В GP-скриптах успешного поиска нет `ellrank`, `ellrankinit`,
`ell2cover`, `ellanalyticrank` или `ellgenerators`.

## Повторный запуск

Из корня проекта, при наличии собранного `RankHunt.dll` и локального PARI:

```powershell
python tools/RankHunt/replay_record_reproduction.py
```

Это повторение **сохранённого, уже подобранного сценария**. Программа начинает
с 17 точек, вычисляет опоры из доступных точек, реально запускает 14 поисков
и выполняет два точных восстановления. Недостающие точки должны появиться
в выводе поиска. По умолчанию каждый вызов ограничен 180 секундами; при
незавершённом поиске сценарий останавливается и сохраняет достигнутый результат.
Новый каталог создаётся в `artifacts/record-replay`.

Сценарий повторения проверен небольшим интеграционным тестом; дорогой полный
повтор после сохранения не запускался. Сами 14 поисков уже выполнены и их
скрипты, входы, опоры и вывод сохранены в `results/record-reproduction-20260914`.

Следующая задача для общего алгоритма — выбирать хорошие модели и короткие
представители без доступа к неизвестным точкам. Успех на этой кривой даёт
проверяемый контрольный пример, но не гарантирует, что нынешняя эвристика
самостоятельно найдёт 31 точку по одному уравнению.
