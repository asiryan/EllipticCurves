# Повторный поиск на рекордной кривой ICARM302

Последующее воспроизведение всех 31 точки и текущие доработки описаны в
[новом отчёте](record-reproduction-20260914.md). Ниже сохранён результат
предыдущего, неудачного эксперимента.

14 сентября 2026 года, запуск `20260914-135923`. Цель — самостоятельно
получить нижнюю границу 31 на фиксированной опубликованной кривой,
начав только с 17 общих сечений семейства. **В этом запуске цель не достигнута:
все три режима сохранили границу 17, новых точек не вернули.**

## Вход и проверка

`tools/RankHunt/record_recovery.py` использует опубликованный параметр
`T=164518/924945`. Существующий C#-экспорт вычисляет 17 точек из общих формул
семейства. Скрипт переводит их на опубликованную модель с масштабом 3,
точно проверяет преобразование всех пяти коэффициентов и принадлежность
каждой точки кривой. C# отдельно подтверждает исходную границу 17.

Опубликованный список 31 точки не загружается ни при подготовке, ни при поиске.
Это эксперимент с 17 начальными точками и известным параметром, а не поиск
только по уравнению и не повторное открытие рекордного параметра семейства.

## Измеренный результат

| Режим | Лимит | Время PARI | Новые точки | Результат |
|---|---:|---:|---:|---|
| `pointed` | 60 с | 6,724 с | 0 | Все 17 опорных точек обработаны, граница 17 |
| `rank`, усилие 2 | 120 с | 120,003 с | 0 | Тайм-аут внутри `ellrank`, граница 17 |
| `covers` | 120 с | 120,017 с | 0 | Тайм-аут внутри `ell2cover`, граница 17 |

Общее время с подготовкой и проверками — **247,145 с**, около 4 минут 7 секунд.
Каждый режим использовал минимальную модель, фиксированное состояние RNG
`20260914` и предел стека PARI 512 МБ. Высота поиска — 100000; максимум опорных
точек/покрытий — 64. В первом режиме вход содержал 17 точек, все они обработаны.
Существующий общий скрипт автоматически объединяет найденное с исходным набором
и получает точный сертификат C# после каждого этапа. PARI не сообщил ошибок.

В журнале второго этапа последняя метка — `RANK_BEGIN`, третьего —
`COVERS_BEGIN`. Покрытия до истечения лимита не были возвращены; поиск точек
на них не начался. Тайм-аут не устанавливает невозможность завершения расчёта
при большем бюджете. Граница 17 описывает только полученный нами набор:
опубликованная нижняя граница этой же кривой по полному набору свидетелей — 31.

Дополнительно проверены 318 ранее построенных квадратичных сечений, дающих
126 различных условий `U²=H(T)`. При рекордном параметре **ни одно** значение
H не является квадратом в Q. Поэтому именно этот сохранённый набор конструкций,
давший нам другие кривые с границей 19, на рекордной кривой дополнительных
рациональных точек не даёт. Проверка использует точные целочисленные корни
числителя и знаменателя; она не перебирает все возможные квадратичные сечения.

## Сохранённые данные и текущий сценарий поиска

В `results/record-recovery-20260914-135923` находятся исходные 17 точек,
их сертификат, итоговый набор, сводка трёх запусков и проверка 126 условий.
Скрипты GP, stdout и stderr каждого этапа сохранены в
`artifacts/record-recovery/20260914-135923`.

После этого эксперимента пользователь уточнил направление: искать точки
и проверять их независимость, без попыток вычислить ранг целиком. Поэтому
из `record_recovery.py` удалены этапы `ellrank` и `ell2cover`. Сохранённые выше
результаты относятся к прежнему сценарию; текущая команда выполняет только
поиск `pointed` и точную проверку нижней границы.

Из корня проекта, с уже собранным RankHunt и установленным PARI:

```powershell
python tools/RankHunt/record_recovery.py
```

Каждый запуск создаёт отдельный каталог с датой и временем. Лимит поиска
по умолчанию — 60 секунд (`--pointed-seconds`); размер области и количество
опорных точек задаются через `--height` и `--anchors`. Проверки и запуск
процессов добавляют время сверх лимита. После поиска фиксируется, достигнут
ли целевой сертификат 31; досрочная остановка непосредственно внутри перебора
по достижении этой границы пока не реализована. При наличии сохранённого пула
сечений скрипт также выполняет описанную быструю проверку условий квадрата.

Следующий содержательный шаг — диагностировать на известных свидетелях,
почему они недоступны текущим представлениям и пределам поиска, затем
повторять эксперимент без передачи дополнительных опубликованных точек
поисковой программе. Этот запуск не воспроизвёл метод авторов и не показал,
что одного увеличения времени будет достаточно.

## Направление дальнейшей работы

1. Зафиксировать кривую ICARM302 и 17 исходных точек. Опубликованные
   дополнительные точки использовать в отдельной диагностике, не на входе
   поискового запуска.
2. Восстановить координаты известных дополнительных точек на вспомогательных
   уравнениях, точно проверить обратные отображения и измерить необходимые
   границы перебора. Это отличит ошибки реализации от неудачного представления.
3. Улучшать выбор опорных точек, преобразования и отсеивание кандидатов
   исходя из этих измерений. Использовать покрытия и другие вспомогательные
   модели только как способ получать точки с приемлемой стоимостью подготовки.
4. Каждую найденную точку проверять точной подстановкой, удалять дубликаты
   с учётом знака и проверять увеличение нижней границы существующим
   сертификатом C#. Отсутствие прироста этого сертификата само по себе
   не доказывает зависимость точки: такой кандидат должен сохраняться.
5. Сравнивать число подтверждённых независимых точек, время поиска,
   число кандидатов и время проверки. Ближайшая контрольная цель — прирост
   сверх 17 на этой же кривой, конечная цель воспроизведения — граница 31.

В этот рабочий процесс не входят вычисление точного ранга, аналитического
ранга, верхних границ, полного пространства Сельмера или запуск `ellrank`.
PARI может использоваться для арифметики, преобразований и ограниченного
поиска рациональных точек. Старые экспериментальные режимы общего
`point_search.py` сохраняются для истории проекта, но текущий сценарий их
не вызывает.
